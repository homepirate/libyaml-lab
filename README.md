# Разбор SPEC-файла libyaml в ALT Linux

Учебный проект по анализу сборки RPM-пакетов в репозитории ALT Linux Sisyphus. Рассматривается спецификация библиотеки `libyaml` версии `6.0.2-alt1`.

LibYAML — библиотека на языке C для чтения и формирования документов YAML 1.1. Она предоставляет программный интерфейс для разбора (parser) и генерации (emitter) YAML.

## 1. Структура репозитория

``` text
alt-libyaml-spec-analysis/
├── libyaml.spec    # Оригинальная спецификация ALT Linux
└── README.md       # Разбор спецификации
```

Оригинальная спецификация: [libyaml.spec ALT Linux](https://github.com/altlinux/specs/blob/sisyphus/l/libyaml/libyaml.spec). Версия и релиз взяты из самого SPEC-файла.

## 2. Преамбула и метаданные

Преамбула содержит сведения о пакете, источниках и зависимостях, а также определения RPM-макросов.

| Директива       | Значение                         | Назначение                                               |
|-----------------|----------------------------------|----------------------------------------------------------|
| `Name`          | `libyaml`                        | Имя исходного пакета.                                    |
| `Version`       | `6.0.2`                          | Версия, указанная сопровождающим в спецификации.         |
| `Release`       | `alt1`                           | Первый релиз пакетирования этой версии для ALT Linux.    |
| `Summary`       | —                                | Краткое описание библиотеки.                             |
| `License`       | `MIT/X11`                        | Обозначение лицензии в RPM-метаданных.                   |
| `Group`         | `System/Libraries`               | Категория системных библиотек.                           |
| `Url`           | `http://pyyaml.org/wiki/LibYAML` | Адрес проекта, записанный в спецификации.                |
| `Source`        | `%name-%version.tar`             | Имя архива исходного кода.                               |
| `BuildRequires` | `doxygen` (условно)              | Явно объявленная сборочная зависимость для документации. |

RPM подставляет значения директив `Name`, `Version` и `Release` в соответствующие макросы `%name`, `%version` и `%release`. Поэтому `Source` раскрывается в `libyaml-6.0.2.tar`.

Закомментированный `Source-url` не является активной инструкцией скачивания. Для локальной сборки необходим подходящий архив из исходного пакета ALT Linux; произвольный архив с сайта проекта может не соответствовать спецификации.

`BuildRequires` описывает зависимости, необходимые при сборке, а `Requires` — зависимости, необходимые установленному бинарному пакету. Компилятор, Make и инструменты Autotools в данном SPEC-файле явно не перечислены: их наличие зависит от стандартного сборочного окружения ALT Linux и его зависимостей.

## 3. RPM-макросы и условная сборка

RPM-макросы позволяют повторно использовать значения и стандартные команды сборки. В этой спецификации особенно важны два определения.

### 3.1. Версия ABI

`%define abiversion 2` задаёт макрос `%abiversion` со значением `2`.

ABI (Application Binary Interface) определяет двоичную совместимость программы и библиотеки. Включение номера ABI в имя пакета позволяет отличать несовместимые поколения библиотеки и при подходящем распределении файлов устанавливать их параллельно.

Выражение `%name%abiversion` раскрывается в `libyaml2`. Это не версия исходного кода, а номер ABI, используемый в имени пакета. Само определение макроса не устанавливает SONAME библиотеки: SONAME формируется системой сборки исходного проекта.

### 3.2. Сборка документации

Макрос `%def_with doc` задаёт включённую по умолчанию опцию `doc`. Конструкция `%if_with doc` проверяет, включена ли эта опция; `%endif` завершает условный блок.

Опция используется в трёх местах:

- подключение сборочной зависимости Doxygen;
- генерация документации в секции `%build`;
- включение HTML-документации в пакет разработки в секции `%files devel`.

При отключении опции пропускаются все три действия, но компиляция самой библиотеки и упаковка обычного файла ReadMe продолжаются.

При наличии исходного архива и настроенного RPM-окружения режим можно выбрать из командной строки:

``` bash
# Сборка с документацией (режим по умолчанию)
rpmbuild -ba --with doc libyaml.spec

# Сборка без документации
rpmbuild -ba --without doc libyaml.spec
```

Второй режим полезен при минимизации сборочных зависимостей.

## 4. Формируемые RPM-пакеты

Из одного исходного пакета формируются два явно описанных бинарных пакета.

``` text
libyaml-6.0.2-alt1.src.rpm
├── libyaml2          # Библиотека для выполнения программ
└── libyaml-devel     # Файлы для компиляции программ
    └── Requires: libyaml2 = 6.0.2-alt1
```

RPM также может автоматически сформировать пакет отладочной информации `libyaml2-debuginfo` в зависимости от настроек сборочного окружения. Отдельная секция для него в рассматриваемом SPEC отсутствует.

### 4.1. libyaml2

Директива `%package -n %name%abiversion` создаёт пакет под явно заданным именем `libyaml2`. Ключ `-n` позволяет использовать полное имя вместо стандартного имени с суффиксом. Соответствующая `%description -n` задаёт его описание.

Пакет содержит версионированные динамические библиотеки, необходимые при запуске приложений, использующих LibYAML, и файл документации `ReadMe.md`.

### 4.2. libyaml-devel

Директива `%package devel` создаёт подпакет с суффиксом `-devel`. Описание задаётся через `%description devel`.

Выражение зависимости `%name%abiversion = %version-%release` раскрывается в `libyaml2 = 6.0.2-alt1`. Оно требует установки точно соответствующего релиза основной библиотеки, чтобы файлы разработки и библиотека были согласованы.

В подпакет входят заголовочные файлы C, файлы для линковки, метаданные pkg-config и, при включённой опции `doc`, HTML-документация.

Для исходного имени `libyaml` отдельный бинарный пакет в SPEC не описан: нет собственной секции `%files` без указания подпакета. Корневая `%description` описывает исходный пакет.

## 5. Этапы сборки

``` text
%prep -> %build -> %install -> %files
```

### 5.1. %prep — подготовка исходного кода

Макрос `%setup` распаковывает исходный архив и переходит к подготовленному дереву исходников (по умолчанию ожидается каталог `libyaml-6.0.2`).

Явных патчей (`Patch` и команд их применения) в спецификации нет.

### 5.2. %build — конфигурирование и компиляция

В секции `%build` используются три основных макроса:

| Макрос или параметр | Назначение                                                                       |
|---------------------|----------------------------------------------------------------------------------|
| `%autoreconf`       | Перегенерация файлов системы сборки GNU Autotools, включая сценарий `configure`. |
| `%configure`        | Запуск конфигурирования с параметрами путей, архитектуры и окружения ALT Linux.  |
| `--disable-static`  | Отключение сборки статических библиотек (`.a`) средствами Libtool.               |
| `%make_build`       | Запуск Make с поддержкой параллельной компиляции.                                |

GNU Autotools формирует Makefile для текущей платформы, после чего Make компилирует исходные файлы C и выполняет линковку.

Параметр `--disable-static` позволяет сосредоточить пакетирование на динамической библиотеке (`.so`). Он задан безусловно; отдельного переключателя для статической сборки в этой спецификации нет.

При включённой опции `doc` выполняется Doxygen с конфигурацией `doc/doxygen.cfg`. Переменные `top_srcdir` и `top_builddir` получают текущий каталог с помощью `pwd` и передаются процессу Doxygen, чтобы он мог найти исходные и сборочные файлы. Результат — HTML-документация, ожидаемая в каталоге `doc/html`.

### 5.3. %install — подготовка файлов пакета

Макрос `%makeinstall_std` выполняет установку собранных файлов в изолированный каталог `%buildroot` с использованием `DESTDIR`.

Это подготовка будущего RPM, а не установка в рабочую систему. Например, библиотека, предназначенная для системного каталога `/usr/lib64`, на данном этапе размещается внутри сборочного корня.

### 5.4. %files — распределение файлов по пакетам

Секции `%files` определяют, какие установленные файлы будут принадлежать каждому бинарному RPM.

| Шаблон или директива | Пакет           | Назначение                                                        |
|----------------------|-----------------|-------------------------------------------------------------------|
| `%doc ReadMe.md`     | `libyaml2`      | Обычная документация проекта.                                     |
| `%_libdir/lib*.so.*` | `libyaml2`      | Версионированные разделяемые библиотеки и соответствующие ссылки. |
| `%doc doc/html`      | `libyaml-devel` | HTML-документация при включённой опции `doc`.                     |
| `%_libdir/lib*.so`   | `libyaml-devel` | Неверсионированные файлы или ссылки для линковщика.               |
| `%_includedir/*.h`   | `libyaml-devel` | Заголовочные файлы C.                                             |
| `%_pkgconfigdir/*`   | `libyaml-devel` | Метаданные для pkg-config, включая флаги линковки.                |

Макрос `%doc` отмечает файлы документации и позволяет RPM разместить их в соответствующем каталоге документации.

Каталоги задаются RPM-макросами вместо жёстко прописанных путей. Например, на x86_64 значения обычно следующие:

| Макрос           | Типичное значение      |
|------------------|------------------------|
| `%_libdir`       | `/usr/lib64`           |
| `%_includedir`   | `/usr/include`         |
| `%_pkgconfigdir` | `/usr/lib64/pkgconfig` |

Фактические значения зависят от архитектуры и настроек RPM. Их можно проверить на ALT Linux:

``` bash
rpm --eval '%_libdir'
rpm --eval '%_includedir'
rpm --eval '%_pkgconfigdir'
```

Такое разделение позволяет устанавливать приложениям только runtime-библиотеку, а разработчикам — дополнительно заголовки и файлы для линковки.

## 6. Тесты и проверки

### 6.1. Функциональные тесты

В исходной спецификации отсутствует секция `%check`. Также нет явного вызова `make check`, запуска тестовых программ или определения переключателя функциональных тестов.

Это означает, что SPEC-файл не предписывает отдельный запуск функциональных тестов LibYAML. Успешная компиляция сама по себе не подтверждает корректность разбора YAML. Наличие тестов в исходном проекте следует проверять отдельно.

Если в используемом дереве исходников реализована цель `check`, спецификацию можно дополнить, например, такой секцией после `%install`:

``` spec
%check
%make_build check
```

Это предложение по улучшению, а не часть оригинального SPEC. В данном репозитории оригинальный файл не изменяется.

### 6.2. Проверки упаковки

Даже при отсутствии `%check` система RPM контролирует прохождение этапов сборки и формирование пакетов. В стандартном окружении также могут выполняться автоматические проверки и обработка файлов:

- проверка наличия объявленных сборочных зависимостей;
- контроль кодов завершения команд сборки и установки;
- сопоставление файлов в `%buildroot` со списками `%files`, включая обнаружение отсутствующих и, при соответствующей настройке, неупакованных файлов;
- автоматическое определение зависимостей и предоставляемых возможностей бинарных файлов;
- обработка ELF-библиотек, прав доступа, документации и отладочной информации.

Точный набор проверок зависит от версии RPM и конфигурации ALT Linux. Проверки упаковки нельзя приравнивать к функциональным тестам библиотеки.

### 6.3. Дополнительная ручная проверка RPM

После сборки можно исследовать метаданные и состав бинарных пакетов. Следующие команды предполагают, что оба RPM находятся в текущем каталоге, а целевая архитектура — x86_64:

``` bash
rpm -qip libyaml2-6.0.2-alt1.x86_64.rpm
rpm -qlp libyaml2-6.0.2-alt1.x86_64.rpm
rpm -qp --requires libyaml-devel-6.0.2-alt1.x86_64.rpm
rpm -qlp libyaml-devel-6.0.2-alt1.x86_64.rpm
```

После установки соответствующих пакетов можно проверить наличие библиотеки и доступность метаданных для разработки:

``` bash
rpm -q libyaml2 libyaml-devel
rpm -V libyaml2 libyaml-devel
pkg-config --modversion yaml-0.1
pkg-config --cflags --libs yaml-0.1
```

`rpm -V` проверяет установленные файлы по данным RPM, а pkg-config позволяет проверить доступность метаданных для компиляции. Для подтверждения поведения парсера потребуются отдельные функциональные тесты. Эти команды приведены как план проверки, а не как отчёт о выполненной сборке или тестировании.

## 7. История изменений и дополнительные особенности

Секция `%changelog` содержит историю пакетирования, начиная с первоначального появления пакета в Sisyphus в 2008 году. Записи показывают дату, сопровождающего, версию и суть изменения.

Для рассматриваемой спецификации важны следующие события:

| Год  | Изменение                                                      |
|------|----------------------------------------------------------------|
| 2008 | Первоначальное пакетирование для ALT Linux Sisyphus.           |
| 2014 | Добавлена генерация и упаковка документации для разработчиков. |
| 2016 | Добавлен переключатель документации для bootstrap-сборки.      |
| 2025 | Версия в SPEC изменена с `0.2.5` на `6.0.2`.                   |

В текущем файле нет пользовательских сценариев `%pre`, `%post`, `%preun`, `%postun`, явно определённых конфликтов, секции `%clean` или специальных ветвлений по архитектурам. Исторические упоминания `ldconfig` в changelog не означают, что соответствующие скрипты присутствуют в актуальном SPEC.

## 8. Вывод

Спецификация LibYAML демонстрирует сборку системной библиотеки с применением GNU Autotools, использование RPM-макросов, разделение runtime- и development-файлов, привязку имени пакета к ABI и условную генерацию документации. Отдельного этапа функционального тестирования в оригинальной спецификации нет; его можно рассматривать как возможное улучшение.

Разбор выполнен статически по оригинальному SPEC-файлу. Исходный архив и бинарные RPM в данный учебный репозиторий не входят; фактическая пересборка пакета не выполнялась.
